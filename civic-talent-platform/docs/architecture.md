# Architecture walkthrough

## Business domain

This original demonstration covers three entities: Candidate, Vacancy and Application. A candidate can apply to a vacancy at most once. Application status follows a finite state machine: `submitted -> reviewing -> interview -> offered`; rejection/withdrawal are alternative exits. This prevents invalid transitions such as instantly offering a newly submitted application.

## Request lifecycle

1. A client sends HTTPS to a load balancer in a real deployment (locally plain HTTP is bound to loopback).
2. The API validates a header key and the JSON schema.
3. A request-scoped database session performs relational checks and commits a transaction.
4. The API returns JSON and a request correlation identifier.
5. Structured logs record path, status and duration without writing application payloads.

## Architecture choices

- **Modular monolith instead of microservices:** simplest correct boundary for a small training workflow. Splitting into services too early adds authentication, network failure and consistency burdens.
- **PostgreSQL:** relational joins, uniqueness and referential integrity suit hiring workflow records. JSON skills are an intentionally limited flexible attribute.
- **REST:** broad compatibility, standardized HTTP error handling and an autogenerated OpenAPI contract.
- **FastAPI/Python:** clear type-aware validation and readable examples. JavaScript/Java client examples show language interoperability.
- **Docker:** makes the app/DB stack reproducible without host-specific installation.
- **Kubernetes:** replica management, rolling updates, health probes and resources; assumes externally provisioned Postgres and registry.
- **AWS ECS/Fargate alternative:** lower Kubernetes operations burden for a single container API. RDS provides managed database hosting. AWS example is illustrative only.
- **IaaS/PaaS/SaaS:** EC2 would be IaaS; RDS/ECS are managed infrastructure/platform building blocks; the delivered recruitment application would be SaaS if operated as a hosted product with tenancy, billing and lifecycle controls (not implemented).

## Production evolution

1. Add tenant separation, roles, OpenID Connect, audited administrative access and integration tests against PostgreSQL.
2. Add Alembic schema migrations, outbox/event publication for notifications and transactional consistency.
3. Add pagination, filtering, idempotency keys and API contract versioning.
4. Add private networking, TLS, cloud secrets, database backups/restore exercises and privacy retention controls.
5. Add monitoring/alerts, deployment rollback, load testing, SLOs and cost budgets.

## Nonfunctional requirements exercise

Pick hypothetical targets: availability 99.9%, p95 API latency under 300ms for standard reads, RPO 15 minutes and RTO 4 hours. These are **proposed design targets, not measured performance or achieved recovery guarantees**. Explain what backup tests, load tests and replication architecture would be needed to demonstrate each.
